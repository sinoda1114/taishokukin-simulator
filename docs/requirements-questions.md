## 1. サイトの作りは「サーバーあり」で確定か

**今の要件書:** 冒頭と §12 Q5 と §14 は「フルスタック」（画面に加えて、保存用のサーバーと DB がある）と書いている。同じ §12 の Q1 だけ「静的 SPA」（サーバーなし、ブラウザだけで計算）が残っている。保存・共有・税率テーブル・利用ログはサーバー前提。

**選択肢**
- **A.** Q1 を撤回する。正本は Q5 / §14（サーバーあり）。
- **B.** 本当にサーバーなしにする。保存・共有・DB・ログインは MVP から外す。
- **C.** 今は決めない（実装者が読んで選ぶ）。

**選ぶと何が変わるか**
- 計算そのものはどれでもブラウザで動く。変わるのは保存と公開の範囲。
- A: いま書いてある F6（保存）・F10（税率テーブル）・F11（ログ）・F12（認証の枠）を載せる前提になる。後から静的サイトに戻すと、保存 URL を捨てることになる。
- B: MVP が「計算ページだけ」に縮小する。あとから保存を足すのは普通にできるが、今の必須一覧を書き直す。
- C: 実装が分岐する。あとが一番高い。

**推奨:** A。2026-09-20 の決定文面と一致する。

## 2. 最初の公開で、保存・共有・ログイン履歴のどこまで出すか

**今の要件書:** F6 は必須で、(1) 匿名でも保存できる共有 URL（share token = 長いランダムな URL の鍵）、(2) ログイン後は自分の履歴の一覧と再編集、と書いてある。F12 / Q7 は MVP ではログインオフ（`AUTH_PROVIDER=none`）。§3.2 は「入力を URL のクエリに載せる共有」を v2 候補として残している。§14 はログイン後に匿名保存を自分のものにする（claim）と書いてある。

**選択肢**
- **A.** MVP は匿名の共有 URL だけ。履歴・claim はログイン導入後。クエリ共有は v2 のまま。
- **B.** MVP からログイン履歴まで出す（ログインを MVP でオンにする）。
- **C.** MVP では保存しない。共有するならクエリに入力を載せる方式だけ（サーバー保存なし）。

**選ぶと何が変わるか**
- 税額の計算式は変わらない。変わるのは「結果をどう残すか」。
- A: 最初の公開は URL を知っている人が試算を見られる、まで。あとから履歴を足せる。claim のルール（他人の URL を自分の履歴に取り込めるか）はログイン導入時に決める。
- B: Clerk（Google ログイン）が MVP の前提になる。Q7「後付け」を覆す。あとから外すのは無駄が大きい。
- C: F6 のサーバー保存を必須から外す。URL が長くなり、金額がアドレスに残る。あとから token 保存を足すことはできる。

**推奨:** A。ログインオフのまま F6 の前半だけを必須にすると、書いてある認証方針と両立する。

## 3. 「みなし勤続」は、前の退職金の控除を引く前で判定するか

**今の要件書:** 前の退職金が、その勤続年数で計算した控除より少ないとき、勤続期間を短く見なしてから重複を見る（§5.5(c)。これが **みなし勤続**）。例は「iDeCo 500万・加入20年 → 控除800万より少ないので 12年とみなす」。ここでの 800万は、重複を引く **前** の普通の控除。一方テスト T9（転職3本）の数字は、iDeCo の控除を重複調整 **したあと**（350万）と比べると 500万 > 350万 なのでみなし無し、とした場合にだけ合う。本文どおり調整前（1360万）と比べると、退職金2との重複は 0 年になり、T9 の「重複5年」は出ない。

T9 のあらすじ: 45歳で退職金1（1300万・23年）→ 60歳で iDeCo（500万・拠出28年）→ 65歳で退職金2（800万・20年）。

**選択肢**
- **A.** 調整前の控除と比べる（本文と §5.5(c) の例）。T9 の退職金2側を直す。
- **B.** その手当自身の調整後控除と比べる。T9 の数字は維持し、本文を直す。
- **C.** 一次情報を確認するまで、T9 を「未確定」にしてエンジンの正に使わない。判定式は仮で A か B を書く。

**選ぶと何が変わるか**
- **計算:** 前の退職金が控除未満のとき、あとの退職金の税が変わる。T9 では退職金2の課税が「100万」か「0に近い」かに割れる（数十万の差になり得る）。
- MVP の画面範囲は変わらない。
- あとから A↔B を変えると、保存済みの試算とテスト期待値がまとめてずれる。計算の芯なので、先に決めた方が安い。C は公開前に必ず A か B へ戻す。

**推奨:** 文書の一貫性だけ見るなら A。どちらが法令かはこの質問では決めない。迷うなら C。

## 4. 同じ年に「DC」と「会社の退職金」を両方受け取ったとき、翌年以降はどっち扱いか

**今の要件書:** 前年の退職金を重複調整に入れるかの年数（**4年 / 9年 / 19年** の窓）は、前の手当が DC かどうかで決める（§5.5(a)）。**DC** は iDeCo や企業型の確定拠出年金の一時金。会社退職金・共済は **一般**。同じ年に複数あるときは「1つの前の退職手当等」にまとめる（東京国税局の文書回答を参照、と書いてある）。まとめた塊が DC なのか一般なのかは書いていない。N本対応は必須（F8）。

例: 2028年に会社退職金と iDeCo を同年受取 → 2032年に別の退職金、のとき、2028年を「4年内の一般」と見るか「9年内の DC」と見るか。

**選択肢**
- **A.** 同じ年でも種類は混ぜず、DC と一般を別々に窓判定する（「まとめる」より「種類ごと」を優先）。
- **B.** まとめた塊に DC が1本でもあれば DC 扱い（窓が広い。調整が入りやすい）。
- **C.** まとめた塊は一般扱い（窓が狭い）。
- **D.** MVP では同じ年に種類の違う手当を入れられないようにする。規則はあとで法令確認。

**選ぶと何が変わるか**
- **計算:** 3本以上で「同年に種類が混ざる」ときだけ、翌年以降の税が変わる。2本だけ（退職金と iDeCo を別年）なら起きない。
- D は入力を制限するので MVP の範囲が少し狭い。A〜C は入力はそのまま。
- あとから D→A/B/C は足せる。A/B/C 同士の切り替えは保存結果がずれる。公開後に変えると「前と同じ入力なのに税が変わった」になる。

**推奨:** 法令をこの場で決めない。製品として穴を先送りするなら D。主ユーザー（退職金と iDeCo を別年で動かす）は D でも試算できる。

## 5. 「同時 / 退職金先 / iDeCo先」の3行は、いつ出すか

**今の要件書:** F2 は必須で、3パターン（同時 / 退職金先 / iDeCo先）の比較。§3.1 は「2本なら」その3つ、と書いている。一方 F8 / F3 は N本（上限だいたい6本）と、受取年を動かす全探索が必須。3本以上のときの「退職金先」が何かは書いていない。会社の退職年が 60歳より前で固定だと、iDeCo 先や同時が制度上できない場合がある。

**選択肢**
- **A.** この3行は「会社退職金1本 + DC1本」のときだけ出す。それ以外は探索結果の表（F3）だけ。
- **B.** 手当がちょうど2本なら、名前が退職金/iDeCo でなくても「同時 / 先 / 後」の3行を出す。
- **C.** 本数が何本でも、この3行を無理に出す（3本以上の「先」は未定義のまま実装者が決める）。

**選ぶと何が変わるか**
- 税の式は同じ。変わるのは結果画面の見せ方と、「同時受取との差額」の基準。
- A/B: 3本以上は F3 の表が本体。あとから3行の見せ方を足せる。
- C: 今すぐ定義が増える。後から「3行の意味」を変えると説明文が全部ずれる。
- 実現できない順（60歳前の退職年固定など）は、A/B なら出さない、で足りる。

**推奨:** A。要件書の「2本なら」と、お手本動画の主ケースに揃う。

## 6. 勤続と重複は「月」で数えてよいか

**今の要件書:** 勤続の入力は開始・終了の年月。重複は **月単位**（§5.5(d)）。一方みなし勤続の書き方は「○年を経過した **日の前日** まで」（§5.5(c)。施行令の言い方）。簡易入力は「勤続年数だけ」で、終了＝退職年、開始＝終了−年数、と月が無い。勤続年数の端数は切り上げ（例 T6: 20年3か月 → 21年）。

**選択肢**
- **A.** 全部月で数える。日は使わない。みなしの「日の前日」も、月の終わりに読み替える。
- **B.** 入力は月のまま、中だけ日に直す（開始＝その月の1日、終了＝その月の末日、など）。
- **C.** 開始日・終了日まで入力させる。

**選ぶと何が変わるか**
- **計算:** 月の境界（ちょうど N 年、みなしの切れ目）で、控除が 40万単位ずれることがある。年の真ん中の差は小さい。
- A: 入力が今のまま。あとから日に上げるなら、保存している「年月」に日を足す作業が要る。
- B: 画面は今のまま。日の規則を変えるとテストが動く。A より条文の言葉に近い。
- C: 入力が増える。主ユーザー（年月までしか覚えていない）には重い。正確には一番寄せられる。

**推奨:** A。要件書がすでに「月単位」と書いてある。日まで持たないと解けないケースを、今の主対象（会社員の退職金と iDeCo）で優先しない。

## 7. 「iDeCo は 60歳から」の 60歳は、何歳の年か

**今の要件書:** iDeCo の受取開始は 60〜75歳。探索もこの範囲（F3、§5.6）。共通入力に **生年月** がある（年齢と西暦の換算用）。必須かどうかは書いていない。実際の制度は「60歳の **誕生月以降**」だが、受取の入力は「年」が基本。加入 10年未満だと開始年齢が 61〜65歳に繰り下がる、と中略である。

例: 1966年7月生まれの人が「60歳で受け取る」→ 2026年（その年に60歳になる）か、2026年7月以降だけか、2027年（満60歳の翌年）か。

**選択肢**
- **A.** 「その年に誕生日を迎える暦年」を 60歳の年とする（1966年7月生まれ → 2026年）。注記で「実際は誕生月以降」と書く。
- **B.** 誕生月を見る。受取年が60歳の年でも、誕生月前は選べない（入力が年だけなら、その年は丸ごと不可、または月入力を足す）。
- **C.** 生年月が空なら 60〜75 をそのまま使い、入っているときだけ A か B。

**選ぶと何が変わるか**
- **計算:** 探索の端が最大1年ずれる。改正の 2026年をまたぐ人では、4年窓と9年窓の境目にも触れる。
- A: 入力は年のままで足りる。生年月は「何歳の年か」の表示用。あとから B にすると、一部の最適年が1年動く。
- B: 正確。年だけの画面だと言い切れないので、受取月を足すか、60歳の年を丸ごと外すかのどちらか。
- C: 未入力を許す。グラフの横軸（60〜75歳）は出せるが、「あなたの60歳」は人によってずれる。

**推奨:** A。受取の粒度が「年」である以上、探索も年に揃える。誕生月まで見るのは、月入力を足すときでよい。

## 8. 退職後も iDeCo 拠出を続ける比較は、金額を動かすか / 2026年12月改正を入れるか

**今の要件書:** F15 は必須。退職後も掛金を続けて勤続年数（控除）を伸ばす比較。入力の「見込み受取額」は1つの円、「拠出終了年齢」は DC だけ任意。額が年数に連動するかは書いていない。§5.6 の **2026年12月改正（予定）** は、加入できる年齢を 70歳未満まで広げる、掛金上限、受給すると加入不可。拠出終了の上限は施行日で切り替える、とある。今の探索上限は「iDeCo 60〜75歳」（受取）。加入できる年齢の現行は 65歳未満側、改正後は 70歳未満。

**選択肢（額と改正をセットで）**
- **A.** 額は固定。動かすのは拠出の年数だけ。2026年12月改正は注意書きのみ（探索の加入上限は現行のまま）。
- **B.** 額は固定、年数だけ。改正後の加入上限（70歳未満）を探索に入れる（フラグか、施行年以降は自動）。
- **C.** 追加拠出で残高も増える、までやる（月の掛金の入力が要る）。改正の扱いは B と同じ。
- **D.** F15 を MVP の必須から外す。退職後拠出の比較は v2。

**選ぶと何が変わるか**
- **計算:** A/B は「同じ残高で控除だけ増える」比較。実際は続けた年の掛金と運用で残高も増えるので、手取りの差は過小になり得る。C は近いが、運用利回りの仮定が入る。
- A: MVP が小さい。改正が施行されたら上限だけ足せばよい。
- B: 施行前に「70歳まで拠出可」で探索すると、今は加入できない年を勧めてしまう。注意書き必須。
- C: 入力と説明が増える。利回りを後から変えると結果が全部動く。
- D: 必須が減る。あとから F15 を足せる。出口の「続けて控除を伸ばす」が、最初の公開では出ない。

**推奨:** A。F15 のポイントは「控除は期間で伸び、最低掛金でも同じ」であり、額を動かす話ではない。改正は予定なので、探索に入れない。

## 9. 小規模企業共済の一括受取を、最初の公開で退職金と同じ扱いにするか

**今の要件書:** 種類に「小規模企業共済」がある。一括受取は一般の退職金と同じ（DC ではない）（§5.5(a)）。§2 の「個人事業主が共済と iDeCo の順を比べる」は v2。§3.1 の MVP には共済の名前がある。受取年を最適化する対象に「共済など」とあり、探索は「任意解約できる年以降」（§3.1）。任意解約がいつも退職所得になるかは書いていない（加入期間によっては退職所得にならない、という話がある）。

**選択肢**
- **A.** 種類として出す。ユーザーが入れた年・額を、一般の退職金と同じ式で計算する。年は自分で指定（自動では動かさない）。「任意解約が退職所得にならない場合あり」と注意する。
- **B.** 種類として出し、解約できる年から受取年を探索する（§3.1 の「など」をそのままやる）。
- **C.** MVP の種類から外す。会社退職金・iDeCo/企業型・その他だけ。共済は v2（§2 に揃える）。

**選ぶと何が変わるか**
- **計算:** A/B は共済を一般扱いで 4年窓。B は探索の組合せが増える（F3 の上限に効く）。C は共済の税を出さない。
- A: 入れたい人は使える。誤って退職所得でない解約を入れるリスクは注意書き頼み。あとから探索（B）を足せる。
- B: 「解約可能年」の入力と、退職所得になる条件が要る。間違えると、退職所得でないお金に控除を当てる。後から直すと過去の最適年が無効になる。
- C: MVP が主対象（会社員 + iDeCo）に絞れる。種類をあとから足すのは容易。

**推奨:** A か C。B は条件が足りない。個人事業主を v2 と書くなら C、種類表を今のまま残すなら A。

## 10. 勤続5年以下のとき、税額を出すか

**今の要件書:** 役員など勤続5年以下は **特定役員**（控除後に 1/2 を掛けない）。役員以外の5年以下は **短期退職手当等**（控除後 300万超は 1/2 なし）。Q4 と §5.2 は MVP では計算しない、注意書きと拡張の穴だけ。入力に「役員だった年数」は無いので、特定役員かは判定できない。原則の退職所得は、控除のあと **1/2** だけが課税対象。T7 は勤続2年 → 控除 80万下限、で 1/2 あり前提の数字。

**選択肢**
- **A.** 税額は出さない（または「計算対象外」だけ出す）。注意書き。Q4 どおり。
- **B.** いつもの 1/2 で仮の税を出し、「5年以下の特例は未反映。実際の税はこれより多いことがある」と強く出す。
- **C.** 短期（300万超は 1/2 なし）だけ仮で掛ける。特定役員は入力が無いので掛けない。同じく強い警告。

**選ぶと何が変わるか**
- **計算:** A は数字なし。B は短勤続だと **過少**（実際より安く出る）。C は短期には寄るが、役員5年以下はまだ過少。
- 主ユーザー（勤続20〜30年）にはどれでも同じ。T7 のような短い勤続だけが変わる。
- A: 「正確性が最優先」と一致。あとから B/C の仮計算を足せる。
- B: 使っている人が数字を信じやすい。警告を弱めると、助言に見えるリスクがある。あとから特例を足すと、同じ入力で税が上がって見える。
- C: エンジンに短期の式を先に入れる。Q4「計算対象外」を一部覆す。特定役員の入力をあとから足す必要は残る。

**推奨:** A。数字を出すなら B（仮だと明記）。C は Q4 を崩すので、特例を本当に入れる版まで待った方がよい。
